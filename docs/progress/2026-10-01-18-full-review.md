## Findings, ordered by priority

### R18-1 — P1: Required Windows enforcement and release packaging are absent

`src/LockIn.Service/Program.cs:21` constructs `NoOpSimulationProvider`; `SimulationEngine.cs:86` explicitly reports `apps = false`. The executable is a current-user console host, not an installed Windows service. There is no release package/build-package helper or complete install/update/repair/uninstall workflow. App selection does not restrict applications. This blocks M5–M8 and the original product definition of done, regardless of frontend polish.

### R18-2 — P2: A transient YouTube evaluation failure leaves an allowed video paused

In `extension/src/content.ts:74`, the metadata signature is saved before `EvaluateVideo` succeeds. An error response or rejected message leaves that signature unchanged. Subsequent ticks skip evaluation for identical metadata, so the checking badge and pause gate remain until navigation, metadata change or release/expiry.

Reproduced by bundling the actual content script with the installed esbuild, executing it in a Node VM with a current-video DOM/runtime fixture, and making the first evaluation fail while subsequent evaluations would return `allow`. After four subsequent timer ticks, both failure variants reported:

```json
{"evaluations":1,"videoPaused":true,"checkingBadgeVisible":true}
```

This is a synthetic fault reproduction, not a live YouTube result. Fix by recording only successfully handled decisions and adding bounded retry/error feedback, while retaining generation checks, redirect deduplication and unconditional expiry/release. Add regression coverage for both rejected messages and `{ error }` replies.

### R18-3 — P2: Profile actions remain available during a pending session review

`MainWindow.xaml.cs:258` allows Duplicate while `_busy`; `SaveDraftAsync` at line 271 obtains the expected revision from mutable `_editing` rather than the reviewed profile's captured save context. New and Send profile again also lack the common busy guard. The review text is frozen, but its later save context is not.

Reproduced with the actual Release WPF app and an isolated host/database:

1. Save a profile at revision 1 and choose Start focus.
2. Leave review pending, navigate to Profiles and click Duplicate.
3. Return to Focus and choose Begin.
4. Observe `Profile changed. Expected revision 0, actual 1.`

Duplicate was enabled; no session started and the original persisted profile stayed at revision 1. Fix the operation boundary consistently: protect profile identity/revision during review and asynchronous saves, prevent conflicting actions, and preserve subsequent draft edits. Add an interaction regression, including backing out of review.

### R18-4 — P1 release gate: Installed and physical-platform acceptance is incomplete

Handoff 14 installed-Brave pairing is historical evidence. This review did not establish installed Brave permission consent, activation and release across the native bridge, live YouTube supported-layout/SPA behavior, the remaining browser restart/race fault matrix, Windows 11, or physical sleep/reboot recovery. Those remain open M3/M4/M6 acceptance cases. Chromium fixtures and a simulated browser actor cannot close these gates.

### R18-5 — P2 release gate: Data controls and retention are missing

Plan section 22.2 requires configurable summary retention and deletion outside active cleanup records. `LocalStore.ListSessions` limits the query to 50 rows; it does not expire stored history. The current UI/protocol has no retention/deletion controls or sanitized diagnostics export. Implement these without deleting active recovery ownership records before accepting M8.

### R18-6 — P2 verification gap: The complete desktop design check did not finish

The fresh `-DesignOnly` run passed first-use/profile/duration and browser-readiness assertions, then failed at `scripts/test-desktop.ps1:235`: UI Automation `TransformPattern.Move(0, 0)` returned “Operation cannot be performed.” Several preceding screenshots contained only a minimized title bar; they are invalid visual evidence. The reason the window was minimized was not established.

Do not count that run as passed. Normalize/check only the test-owned window state before geometry checks, reject minimized screenshots, then rerun the complete design check. Historical handoff 17 compact/focus results remain historical. Screen-reader, high-contrast and physical DPI/scaling acceptance remain open independently.
